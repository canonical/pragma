# Getting Started

This guide walks you through adding Pragma to a React project. By the end, you will have components rendering with correct styles, fonts, and theming.

## Prerequisites

- **Node.js** 22.12+ or 24+
- **React** 19+
- A bundler that resolves `node_modules` CSS imports (Vite, webpack, Next.js, etc.)

## 1. Install packages

The minimum set of packages for using components:

```bash
bun add @canonical/react-ds-global @canonical/styles @canonical/ds-assets
```

`@canonical/styles` aggregates the CSS reset, design tokens, modifier classes, grid utilities, and spacing scale into a single import. `@canonical/ds-assets` provides the Ubuntu Sans font files and icon assets.

If you also need form components:

```bash
bun add @canonical/react-ds-global-form
```

## 2. Import styles

In your application entry point (`main.tsx`, or your framework's root layout), import the global stylesheet and fonts:

```tsx
import "@canonical/styles/fonts";
import "@canonical/styles";
import "@canonical/react-ds-global/index.css";
```

**Order matters, and it matters first.** Import these before your routes and before any component, because the cascade fixes the layer order from the first `@layer` statement it reads: whatever reaches the page first decides how everything after it is arbitrated. In practice that means the stylesheet import is the first line of your entry file, above the route imports.

The fonts import loads the `@font-face` declarations for Ubuntu Sans; font faces are not sorted by the cascade, so they sit outside the layers. The main styles import brings the reset, the design tokens, the typographic engine, the modifier classes, the grid system, and the spacing scale, each in its own cascade layer.

The third import is every component stylesheet in one file, and what it buys is presence rather than position: components import their own CSS from their own modules, so without it a component's rules reach the page only when the code that renders it does, and a lazily-loaded route paints before its styles arrive. It does not decide which of a component's rules and yours wins a tie — both copies reach the build and a minifier keeps the last — and once the component stylesheets carry their `ds.components` layer, the cascade settles that by layer instead of by position.

## 3. Declare the root

Those stylesheets do nothing until the document says where the design system applies:

```html
<html class="ds app comfortable">
```

| Class | What it means | Values |
| --- | --- | --- |
| `ds` | This subtree is the design system's. Its element-level rules — the reset, the typographic engine — apply inside it and nowhere else. | required |
| context | The kind of surface, which selects the comfortable/dense pair for every density value. | `app`, `site` or `docs` |
| density | Which of that pair is in force. | `comfortable` or `dense` |

`ds` does not have to be on `<html>`. Put it on a `<main>`, a section, or one component's wrapper and only that subtree becomes the design system's — which is what makes the package adoptable in an application still built on something else.

## 5. Verify theming

Pragma supports light and dark themes through paired token values. **While no `light` or `dark` class is on the root**, the operating system's preference is followed via `prefers-color-scheme`; adding either class pins the scheme and the OS preference stops applying to that subtree. To force a theme, add `className="dark"` or `className="light"` to any ancestor element:

<Canvas of={Stories.ThemeForcing} />

No JavaScript runtime or theme provider is required.

## Cascade layers

Every rule the design system ships sits in a named cascade layer, and one statement fixes their order:

```css
@layer normalize, ds.tokens, ds.reset, ds.typography, ds.modifiers, ds.surfaces,
       ds.states, ds.components, ds.components.global, ds.components.app;
```

Read from the bottom up, each name is an argument about who should win: component rules beat the modifier classes, which beat the reset, whatever order the files happen to load in. Two consequences are worth knowing before you write any CSS of your own.

- **Unlayered CSS beats all of it.** That is what the cascade says: a rule in no layer outranks every rule in one. So your own stylesheet wins by default — deliberately — and if you would rather it did not, put it in a layer of your own and name that layer in your own statement, prepended before this one.
- **`!important` inverts the order.** For important declarations the earliest layer wins, which makes an important rule in the lowest layer the strongest thing on the page. The design system ships none.

The `@canonical/styles` README's **Cascade layers** section is the reference: what is layered where, what is deliberately left unlayered, and why the element-level layers are scoped to `ds`. A longer explanation of the contract — the reasoning rather than the table — is being written as `docs/explanations/CASCADE.md` in the pragma repository.

### Checking the layers on a built page

Do not grep your built CSS for the statement above. A minifier rewrites it: Lightning CSS, which Vite uses, merges the blocks that share a layer name, reorders them into the order the statement declared, deletes the statement, and emits a statement only for a declared name that no block establishes. The order survives; the text does not.

Read the layers from the page instead. In devtools, on a page that has loaded your stylesheet:

```js
[...document.styleSheets]
  // A stylesheet served from another origin refuses to be read; skip it.
  .flatMap((sheet) => { try { return [...sheet.cssRules]; } catch { return []; } })
  .filter((rule) => rule instanceof CSSLayerBlockRule || rule instanceof CSSLayerStatementRule)
  .map((rule) => rule.name ?? rule.nameList.join(", "));
```

The names come back in the sequence the browser applies them, which is what the statement was for: on the reference build that sequence is exactly the ten declared names. A layer's position is fixed the first time it is named, whether by a statement or by a block, and only the unlayered at-rules the cascade does not sort (`@font-face`, `@property`, `@keyframes`, `@charset`) may appear before the first of them.

## Vite configuration

Vite works out of the box with no special configuration. The CSS imports from `@canonical/styles` resolve through `node_modules` via Vite's built-in CSS handling.

If you use a custom `css.transformer` or `css.modules` configuration, ensure that `@canonical/styles` is not processed as CSS Modules — it uses global class names by design.

## Next.js configuration

For Next.js projects, import styles in your root layout, above everything else it imports, and mark the root element there:

```tsx
// app/layout.tsx
import "@canonical/styles/fonts";
import "@canonical/styles";
import "@canonical/react-ds-global/index.css";

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en" className="ds app comfortable">
      <body>{children}</body>
    </html>
  );
}
```
