# PaginationBar recipes

`PaginationBar` is the bar beneath a collection's rows: how many items a page holds, which are on screen out of how many, and the way to every other page. It pages a provider's window and nothing else — the provider owns the query, the source answers it, and the bar only asks for another window.

It takes its provider explicitly, as `DataTable` does. A table used on its own gets the same footer as one composed inside a `DataViews` root, and the bar never behaves differently because some context happened to be present. Inside a root, `DataViews.Pagination` renders this same bar for the root's provider.

The page size and page selects are the design system's `SelectInput`, and the page controls are drawn as its `Button` — a real link where the page can be reached, a disabled button where it cannot. The select's chrome comes from the `@canonical/react-ds-global-form` stylesheet, so load it on the page beside `@canonical/styles`:

```css
@import url("@canonical/styles");
@import url("@canonical/react-ds-global-form/dist/esm/index.css");
@import url("@canonical/dataviews-react/index.css");
```

## A table and its pagination bar

Build the provider once, in state, over the module-scope collection and its source, and hand it to both parts. Nothing runs until one of them observes it: the table and the bar each observe the provider for as long as they are mounted, the first observer runs the source and asks for the first page, and the last to leave stops it. The two read the same provider: the bar asks for a window, and the table shows the rows that answer it. The window the provider starts on is in its `snapshot`.

```tsx
import {
  createArraySource,
  createDataViewsProvider,
} from "@canonical/dataviews-core";
import {
  DataTable,
  PaginationBar,
  type DataTableColumn,
} from "@canonical/dataviews-react";
import { useState } from "react";
import { machineCollection, machines } from "./machines.js";

const columns: readonly DataTableColumn[] = [
  { id: "name", header: "Host" },
  { id: "status", header: "Status" },
  { id: "region", header: "Region" },
  { id: "owner", header: "Owner" },
];

export function Machines() {
  // Built once: the parts observe it, which starts its source.
  const [provider] = useState(() =>
    createDataViewsProvider({
      collection: machineCollection,
      source: createArraySource({
        rows: machines,
        collection: machineCollection,
        searchFields: ["name", "owner"],
      }),
      snapshot: { query: "page=1&size=5", presentation: {} },
    }),
  );
  return (
    <>
      <DataTable provider={provider} columns={columns} label="Machines" />
      <PaginationBar provider={provider} sizes={[5, 10, 25]} />
    </>
  );
}
```

`sizes` are the page sizes on offer: 50, 75 and 100 unless you say otherwise. The applied size is always among them, so a provider started on a size you did not list still shows it. Choosing a size returns to the first page, because the old page number counted rows of a different size.

## Counts it can stand behind

Every count describes the rows on screen, and every page control goes somewhere the collection can reach. A source that counts the rows the window pages over exactly — `counts.pageable` declared `"exact"` — gets a page total and a last page. One that counts them loosely — a lower bound — has the bound said as one ("out of at least 40 items"), no last page invented from it, and — on a source paged by number — Next offered while the bound proves a page past this one; on a source paged by token, the token alone says where the next page starts. One that counts nothing gets neither: the summary counts the rows on screen, Last is unavailable, and Next is taken from the page's own word that more exists, or, failing that, offered while the page is full, the only evidence left that there may be another.

A source that reaches its pages only through tokens — `pagination.kind` declared `"cursor"` — is paged by those tokens: Next carries the one the current page handed back, Previous the one before it. Such a source may still count its rows exactly, and the summary says so, but no page total is shown and Last stays unavailable, because a page number addresses nothing there.

<Canvas of={Stories.WithoutACount} sourceState="none" />

While the rows on screen do not answer the current query — nothing has arrived yet, a replacement query is loading, or the request failed and left an earlier query's rows in view — the summary says nothing. A count belongs to the query and page size that produced it, not to the page: through a page move of the same query the page total and its destinations stand, and the summary alone waits; a new query or page size drops the count until the source answers for it. A total from an earlier query is not this one's.

<Canvas of={Stories.Loading} sourceState="none" />

The summary is a polite status. It names the rows on screen — "Showing 6–10 out of 12 items", or "Showing item 11 out of 12" for one — and speaks when settled results change what it says, so moving to another page or narrowing the collection is announced, and a background refresh with the same answer is not. When a page control that has the focus becomes unavailable — Next while its page loads, Last on arriving at the last page — the focus moves to the page select rather than to the document.

## Before any script runs

With a location, every page the bar can reach is a link the provider's encoder spelled, carrying the whole query and the location's other parameters, so paging works before any script runs and a page opens in a new tab like any other link. Pass your router's `Link` as `LinkComponent` and the links render through it, against the design system's shared link contract; the router navigates, and the provider hears the move through its location port. The page size and the page select each sit in a GET form beside hidden controls carrying the rest of the query, with a submit control that is hidden once scripting is enabled. Once it is, a plain click or a submission moves the window in place through the provider instead of navigating; a modified click is left to the browser. Without a location there is no destination a link could lead to, and the page controls are buttons only the enhancement drives, hidden until it runs.

## Sticky at the bottom

The bar holds to the bottom edge of whatever scrolls it and paints the surface it sits on, so the rows scrolling beneath it never show through. A sticky element cannot leave its parent's box, so make the bar a direct child of the scrolling container, beside the table — not the only child of a wrapper its own height.
