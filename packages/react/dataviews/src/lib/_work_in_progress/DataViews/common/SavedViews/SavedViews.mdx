# DataViews.SavedViews recipes

`DataViews.SavedViews` is the collection's saved views: which view is open, whether the query has moved away from it, and the way to switch, save, save as, rename and delete. It reads the views of the enclosing root's provider, which holds the store the application gave it. The part takes a name and nothing else: the views, the open one and the query all belong to the provider.

A saved view is a named query. Opening one applies its query on the first page; the filters, the table and the pagination bar follow, because they read the same provider. The view is *modified* while the live query differs from the one it was opened or saved at. The page, the selection and the arrangement never count.

## Saved views in a composition

Views live in a store the application creates and gives to the provider. `createIndexedDBViewStore` keeps them in the browser's IndexedDB, and it is imported from its own entry point, `@canonical/dataviews-core/indexeddb`, so an application without views never bundles it. The same store keeps the viewer's arrangement, so it is given to the provider twice — as `views` and as `presentation` — as the code beneath this story does. Declare one store for as long as the application runs, and give it to each provider built for the collection.

## The store's scope

The store's scope — its database, the collection and an opaque partition such as the signed-in account — is fixed when it is created; the `@canonical/dataviews-core` README describes each. When the account changes, create a store for the new partition and a provider over it, and mount the parts on that: the old provider stops when its last root unmounts, and nothing reads its store after.

## Saving, saving as, renaming

**Save** writes the live query into the open view, and **Revert** applies the view's query again. **Save as…** saves the live query, and the arrangement in force, under a new name, and opens the new view. **Rename…** renames the open view. A name that is empty, or already another view's, is refused beside the input before anything is written.

Every outcome is said in a polite status. A save that did not happen never reads as saved: a failure names its reason, and the store is never replaced by one in memory.

## Two tabs editing one view

Every edit names the revision of the view it was made against. When another tab saved the view first, saving here is a conflict, not a silent overwrite. The stored view becomes the open one: **Overwrite** saves this tab's query over it, **Save as…** keeps both, and **Discard changes** applies the stored query when this collection can read it.

## Deleting

**Delete…** asks first, naming the view, with the focus on Cancel. The view goes; the query it applied stays, so the rows on screen do not change.

## The arrangement

The arrangement in force — column widths, column order and which columns are hidden — comes from four places, each over the one before, key by key:

1. what the columns declare: their sizing, their order, every column shown;
2. the viewer's default arrangement;
3. the arrangement the open view was saved with;
4. the viewer's own changes to the open view.

It is the provider's `presentation`, and every table on the provider reads it: two tables never disagree on a width, and opening a view re-arranges them all at once. A resize is saved as the viewer's own: to the open view's preferences, or to the default arrangement while no view is open. It never changes the arrangement a view was saved with, so a view stays the same for anyone who opens it again from its saved state. Save as carries the arrangement in force into the new view; Save writes the query alone. A width outside a column's declared bounds is held to them; an order naming a column the table does not have ignores it, and a column the order does not name keeps its declared place; a column declared `hideable: false` is never hidden, and at least one column always shows. The URL carries no arrangement: a link opens with the viewer's own, beneath the saved arrangement of any view it names.

The arrangement lives in the store given as `presentation` — the IndexedDB store here, a `localStorage`-backed store or the application's own server preferences, anything with `readPresentation`, `patchPresentation` and `subscribe`. Given none, it lives in memory for the session: resizing and returning a column to its declared width still work, and nothing claims they were saved.

## Keeping the query in the URL

Give the provider a `location` — `createPlatformLocation(platform)` over your router's platform surface — and opening a view is an edit like any other: the provider applies the view's query and writes it to the URL itself, with the view's id beside it as `view=<id>`, in one entry Back returns from; reverting to the view, or leaving it, respells that entry in place. Nothing else is wired. A reload reopens the view the URL names once the views are listed, marked modified if the query in the URL has moved from it; the id itself never counts as a change. The query works in any browser, while the view lives in this browser's storage: where no stored view answers to the id — another browser, or a deleted view — the id is dropped from the URL and the query stays.

## When storage is refused, and without JavaScript

A browser can refuse storage: a private window, a site setting, a full disk. The control then says views are unavailable and why, with a way to try again, and the rest of the collection works as before.

On the server, and in a browser without JavaScript, the control renders only a notice that saved views need JavaScript: a server cannot read the browser's storage. A link carrying a query still works there, since the query is in the URL.

## No store, no views

A provider created without `views` has none: `provider.views` is `null`, and `DataViews.SavedViews` throws inside its root rather than keep views in memory that a reload would lose. The arrangement is not views: it exists on every provider, in memory without a `presentation` store. To keep views elsewhere — a backend of your own — implement the `ViewStore` contract, which the package root exports, and pass that instead.
