# DataViews.Filters recipes

`DataViews.Filters` edits the collection's query. It takes no query and no list of fields: which fields it offers comes from the collection's schema, and which operators each accepts comes from what the provider's source declares it can execute. It never offers a restriction the source would refuse, and it has no draft to keep in step with the applied query — each edit is the applied query.

The design has not drawn the filters yet, so the part renders plain form controls: a group of checkboxes for a choices field — any of the options, or none of them — a from and a to bound for a number or date field, one checkbox for a flag, and a text input for the text a text field must contain or start with.

## Filters over a composed collection

The collection is declared once, at module scope, and the provider is built over it and a source: the filters read the schema from the one and the capabilities from the other. `labels` names the fields for the reader; a field without a label is named by its field name.

```tsx
import {
  createArraySource,
  createCollection,
  createDataViewsProvider,
} from "@canonical/dataviews-core";
import {
  DataTable,
  DataViews,
  type DataTableColumn,
} from "@canonical/dataviews-react";
import { useState } from "react";
import { type Machine, machines } from "./machines.js";

// Every field and its kind: the kind decides which filter a field offers —
// text is filtered by what it contains — and how the rows order
// by it. Declared once, beside the identity every machine carries.
const machineCollection = createCollection({
  identify: (machine: Machine) => machine.id,
  fields: [
    { field: "status", kind: "choices", options: ["running", "failed", "pending"] },
    { field: "cores", kind: "number", min: 1 },
    { field: "name", kind: "text" },
    { field: "region", kind: "text" },
    { field: "owner", kind: "text" },
  ],
});

const columns: readonly DataTableColumn[] = [
  { id: "name", header: "Host" },
  { id: "status", header: "Status" },
  { id: "cores", header: "Cores" },
  { id: "owner", header: "Owner" },
];

export function Machines() {
  // Built once: the parts observe it, which starts its source and ports.
  const [provider] = useState(() =>
    createDataViewsProvider({
      collection: machineCollection,
      source: createArraySource({ rows: machines, collection: machineCollection }),
    }),
  );
  return (
    <DataViews provider={provider}>
      <DataViews.Filters labels={{ status: "Status", cores: "Cores" }} />
      <DataTable provider={provider} columns={columns} label="Machines" />
    </DataViews>
  );
}
```

## The applied query, not a draft

A checked status, a filled bound or text typed into a text field is the restriction in force. A query the provider starts on — a `snapshot`, a view it opens, a URL it adopts — shows in the controls the same way, and from inside the root the same edits are made in code through this root's filter handles: `useDataViews(machineCollection).filters.status.isAny.set(["failed"])`. The handles are the root's, not the provider's: two roots over one provider share the applied query and never each other's half-typed input.

## Text a field contains or starts with

A text field is filtered by the text its value contains, or the text it starts with, compared case-insensitively: `web` finds `WEB-01`, and starting with `web` finds `WEB-01` but not `api.web`. The text is taken literally — `%` and `_` are characters to look for, never wildcards, and nothing is trimmed. Emptying the input is incomplete rather than a removal, so the text already applied stays until the clear button removes it. A source offers the input only on the text fields it can look through; the REST API stories show one that looks through some fields and not others, and the GraphQL API stories one that looks through all of them.

## Counts beside the options

A provider asked for facets — `createDataViewsProvider({ collection, source, facets: ["status", "cores"] })` — has its source count, over every record the query matches, how many hold each option, and find the least and greatest value a number or date field holds. Filters shows each count beside its option and each end of the range beside its bound, as a description of the control rather than part of its name. A field's own restriction is left out of its own facet, so with failed machines kept the other statuses still show how many machines they would add. Nothing is counted from the rows on screen: while no result answers the applied query, no count is shown.

A choices field whose options are the server's — declared with no `options` list — takes its options from the facet, with any option the set already holds kept beside them.

## Any of, or none of

A choices field is filtered by the options a record is any of — the checkboxes named by the field, `status=failed` — or none of — named `status__isNone`. While a set stands and the source declares the other operator, the set moves there in one step: a real link before any script runs, a button once it does. A set never moves onto one already standing, so no restriction is overwritten.

## An invalid edit keeps the restriction

A bound outside the schema's bounds is refused, not applied — by the schema, and natively by the browser, since a number bound is a native number input carrying the schema's `min` and `max`. The restriction already in force stays in force, and the message beside the input says so, because the value on screen is no longer what filters the rows. A valid edit the source refuses is kept out the same way, with the source's reason beside the input. Emptying a bound is incomplete rather than a removal; the clear button removes it.

## Before any script runs

The filters are a GET form. Each control is named as the URL spells its clause — `status` repeated once per chosen option, `owner__isSet`, `cores__gte`, `name__contains` — and the rest of the applied query rides hidden beside them, so a submission lands on the destination the provider would have written, from the first page. Once scripting is enabled every edit applies as it is made, a submission is intercepted, the submit control is hidden and the clear buttons appear.

## Only what the source can run

A field the source does not declare filterable gets no control. Here the source cannot filter by cores, so there is no cores bound, even though the collection's schema names the field.
